## 0. What the renderer can ACTUALLY do today (code-verified capability base)

Every capability below is grounded in the renderer as it exists — none is invented:

| Capability | Renderer mechanism (verified in code) |
|---|---|
| **C1 static presence** | Any of ~65 `SCENE_ICONS` in `motifs.tsx` REGISTRY; a prop `type` not in REGISTRY renders `null` (silently — this is the failure the compiler must prevent upstream) |
| **C2 continuous motion** | Every motif is a pure function of local frame (`useCurrentFrame`); e.g. MoneyRain falls, Water churns via per-frame offset, clouds drift, rain falls. Motion is PER-MOTIF and hardcoded — the compiler cannot command "move left" |
| **C3 state transition** | `spec.stateIndex` (schema.ts:392) — a static step selector consumed by stateful motifs (FiveRegimes steps 0..4, etc.). It is a DISCRETE pose, not an animated morph; nothing links two props' states over time |
| **C4 spatial relation** | `spec.x, spec.y, spec.scale` — explicit placement; plus `enter` animation (`enter(spec.enter, frame, fps)`) with pop/fade/slide timing |
| **C5 relational drawing** | LIMITED: `arrow` is a FIXED SVG path (`M20,150 Q180,20 320,90`, motifs.tsx) placed by x/y/scale only — its endpoints are NOT parameterizable and its direction (left-low → right-high rise) is BAKED IN; `dominoCascade` chains a fixed fall sequence; there is NO generic "object A transforms into object B" primitive |
| **C6 per-cast action** | `pose(spec.action, frame)` (Scene.tsx:105) — cast poses/locomotion, enum-driven; irrelevant to props |
| **C7 sets & atmosphere** | `bg.set` (26 sets), gradient colors, texture, per-scene accent (`transition.color`) |

**Capability model (the compiler's output vocabulary — exactly 5, per operator list,
each mapped to a verified mechanism):**

```
staticPresence   → C1  (icon exists and is placed)
visibleAction    → C2  (the chosen motif's OWN hardcoded motion — enumerable per motif,
                        not commanded; e.g. water=churn, moneyRain=fall, storm=flicker)
stateTransition  → C3  (stateIndex step, only for motifs that consume it)
temporalRelation → C4  (enter timing: at/duration ordering across props)
spatialRelation  → C4/C5 (band placement + arrow/relator between bands)
```

Rule: the compiler may only CLAIM a capability the target motif verifiably has.
`rain → runoff → flood` as ONE object is unclaimable (no such primitive — C3 is
per-prop, nothing links props); showing it via unlinked props is PROHIBITED (§1).

## 1. Three-level representability (replaces v1's binary)

Motif-enum membership ≠ representable. Classification is per authored VISUAL CLAIM,
not per icon:

```
REPRESENTABLE   — every capability the claim needs is verifiably available
                  (e.g. "a storm is present": C1 ✓, C2 storm flicker ✓)
PARTIAL         — the claim's core nouns are showable, but its action/relation
                  exceeds capability; the parts that CAN be shown are named
UNREPRESENTABLE — no honest mapping exists; nothing is staged for that claim
```

**Worked example — ITW #029 (the operator's own classification, formalized):**

| Authored claim | Verdict | Reason (capability terms) |
|---|---|---|
| storm present over the wash | REPRESENTABLE | C1 `storm` + C2 flicker |
| flash flood in the channel | REPRESENTABLE | C1 `water` + C2 churn |
| desert wash setting | PARTIAL | no set matches (`bg.set` enum lacks desert/arroyo); horizon + palette carries it, but the SET is not the wash — pixel-evidence for the setting must not be claimed |
| rain → runoff → flash flood as one transformation | UNREPRESENTABLE | C3 is per-prop; no linked-states primitive; staging 3 unlinked props would MISREPRESENT the claim (worse than not staging) |

So #029 is `PARTIAL` overall: stage the two REPRESENTABLE claims, mark the setting
PARTIAL, do NOT stage the transformation as fake props — the unrepresentable claim is
named in the ledger with its reason. **The compiler output therefore carries, per
claim: `{claim, verdict, capabilitiesRequired, capabilitiesAvailable, props?[]}`.**

## 2. Evidence-strength taxonomy (replaces v1's `twoSided(pictorial)` naming)

Three separate categories; only the third is a semantic verdict, and it is NEVER
machine-generated:

```
structuralEvidence  — config contains the objects the author named
                      (machine-verifiable: stagedPoles + perPoleIcon, today's logic,
                       compositionCoversBoth shortcut UNCHANGED)
pixelEvidence       — objective, machine-computed properties of the rendered frame
                      (render-truth.js: region luma/chroma/contrast, non-blank,
                       animation delta between frames) — what P10.1's pixel-check did.
                      `"verified"` requires ALL THREE: a BOUND MEASUREMENT RECORD
                      (config hash → still paths → artifact path, written by the
                      render-verify step §7), the recorded config hash MATCHING the
                      config being judged, and the measurements PASSING the defined
                      render-truth.js thresholds. An existing record alone is never
                      sufficient. HASH SCOPE (no cycle): the record lives as a
                      SIDECAR artifact in the audit directory — it is NEVER embedded
                      in the config; the hash covers the canonical JSON of the exact
                      rendered scene config with audit-sidecar fields excluded by
                      explicit enumeration; the record references the hash (one
                      direction only), so hashing the config cannot depend on the
                      record.
independentSemanticJudgment — a HUMAN (operator blind review) judges whether the
                      viewer understands the relation. The machine NEVER derives it
```

Reporting change (report-level only, no gate behavior change): every authored
proposition verdict now reports
`evidenceStrength: { structural: "composition"|"perPole"|"none", pixel: "verified"|"unverified" }`.
`staged-pictorial` is retired as a name; perPoleIcon presence simply strengthens
`structural` from `composition` to `perPole`. Nothing about a PASS changes until the
operator flips a policy — **live publish gate behavior unchanged (v2 rule)**.

## 3. Single integration point (chain verified against the real call order)

`plan-antidote.js` chain (verified): Director → semantic adapter → contract repair →
visual strategy → proposition staging → authorship lock. The compiler hooks in at
**ONE point: immediately after proposition staging, BEFORE the authorship lock** —
because (a) the proposition stager has already claimed the levers it owns, so the
compiler can see what remains, and (b) the authorship stamp must be the LAST writer.

**Precedence contract (who wins a contested lever) — test-enforced, in priority order:**

| Contested resource | Winner | Mechanism |
|---|---|---|
| scene.shot | visual strategy / proposition stager | compiler NEVER touches shot |
| texts / narration / captions | existing pipeline | compiler NEVER writes texts |
| character slots | brief's cast decisions | compiler NEVER writes characters (v1 `forbidden:["cast"]` respected) |
| scene.props slots | **first-writer-wins by named owner** | compiler may ADD but never MUTATE or REMOVE existing props — existing prop objects stay byte-identical (no `_owner` field injected into them); ownership is recorded OUT-OF-BAND in `_authorship.visualCompiled.props[]` (a map: array index of compiler-added props → their claim/verdict/band), so old and new props are distinguishable without touching foreign objects; a compiler prop whose `type` already exists on the scene → dropped to `unrepresentable/duplicate`. STAMP EXCEPTION (per §3a): compiled claim-bound types are appended to the already-created `_authorship.propTypes` at the post-staging/pre-lock hook — the ONE sanctioned post-creation stamp extension |
| scene.diagram | proposition stager | compiler never writes diagram |
| `_authorship` fields | authorship lock | compiler writes ONE new field `_authorship.visualCompiled`; never mutates others |
| forbidden objects in final scene | **firewall, not compiler** | final-scene sweep runs at lock time: any prop whose `type`/narrative noun matches the brief's `forbidden` list → gate violation `FORBIDDEN_OBJECT_STAGED` (REPORT first); this catches EVERY writer, including the Director |

Provenance firewall: compiler output passes through the existing firewall fields
(`allowedMotifs`/`forbiddenMotifs` in schema.ts firewallProvenanceSchema) — compiled
props must be within `allowedMotifs` ∪ world palette; the firewall judgment stays
exactly where it is today.

### 3a. Authorship linkage — how the gate verifies a compiled prop is authored

**Problem (operator finding):** the gate's prop check (authorship.js:124-128) accepts
a prop only if its `type` is in `_authorship.propTypes`. A compiler-added prop not
listed there produces `ENGINE_INVENTED_PROP` — the v2 design would have failed the
authored beats it was meant to serve.

**Contract (operator's ordering, verified against plan-antidote.js: the stamp is
created at :988, staging at :1102, the lock at :1118):**
1. The compile hook runs AFTER `stageProposition` (:1102) and BEFORE the
   `_authorship.lock` seal (:1118) — exactly one point, inside plan-antidote. The
   stamp already exists at that point, so compiled prop types are APPENDED to the
   existing `_authorship.propTypes` array. This is the ONE sanctioned post-creation
   extension of the stamp, and it is legal precisely because the lock has not yet
   sealed props/propTypes: the lock then seals the combined set exactly as it seals
   any staged prop today. No stamp field changes shape; no other stamp field is
   touched after creation.
2. `_authorship.visualCompiled` (new field, written at the same hook point, before
   the lock) carries the full provenance: the claims ledger, the out-of-band
   ownership map (§3), and the capability verdicts.
3. Gate behavior otherwise unchanged — and stated accurately (operator correction):
   the gate's prop check verifies ONLY that every staged prop is in the allowlist;
   it does NOT check the reverse (an allowlist entry never staged is NOT caught by
   that check). The reverse direction is NOT provable by the gate OR by the lock:
   the lock seals what the scene HAS and catches LATER drift — it cannot prove an
   allowlisted type was ever staged. The reverse-direction gap is therefore checked
   in TESTS via the claim ledger (T8c): every claim whose verdict is
   REPRESENTABLE must appear either as a staged prop or as an explicit ledger
   entry; a REPRESENTABLE claim that left neither a prop nor a record is a test
   failure. `FORBIDDEN_OBJECT_STAGED` (§3) covers the sweep at lock time for ALL
   writers.

**Integration test (new T8b):** plan a beat whose brief has a `visual` block → run
plan-antidote → evaluateAuthorship on the produced config: ZERO `ENGINE_INVENTED_PROP`
violations; every stamp field except `propTypes` (appended at the post-staging hook,
per §3a.1) and `visualCompiled` (new) is bit-identical to the no-visual-block
baseline; pre-existing prop objects are untouched (byte-identical) by the append;
remove the `visual` block → config is byte-identical to HEAD behavior.

**Registry note:** the compiler's type contract is the REGISTRY (every type the
renderer draws), NOT `SCENE_ICONS` (which is only the illustration-shot icon
vocabulary — e.g. `door` renders fine but is not in it). See §6 T2.

## 4. Layout: beyond deterministic bandToXY (operator point 5)

The single layout function becomes `composeFrame(props)` with explicit, testable rules
(also pure, no pixels):

1. **Safe area** — existing `motifSafeClamp` semantics reused as the target: no scaled
   box center outside the safe rect.
2. **Non-overlap** — two-pole minimum distance rule: the bounding boxes of pole-0 and
   pole-1 props (scaled) must not intersect by more than 15%; relator (arrow) is
   EXEMPT (it must span them).
3. **Relator target — computed from REAL geometry (operator fix 1):** the arrow's
   path is a fixed SVG curve; `composeFrame` computes the arrow's ACTUAL endpoints by
   transforming the real path's start/end vertices (`M20,150` / `320,90` in the
   360×200 viewBox) through the prop's box placement (x, y, scale). The certificate
   asserts those computed endpoints fall within the pole-0 and pole-1 boxes
   respectively. The arrow's direction is BAKED (left-low → right-high); a claim
   needing any other direction/arrangement (downward, right-to-left, vertical) is
   UNSUPPORTED → ledger entry `relator-orientation-unsupported`, never staged. The
   P10.1 "arrow into empty space" bug becomes a compile error or an honest ledger
   entry — never a rendered surprise.
4. **Foreground/background** — scale bands (`s/m/l/xl`) map to depth: background
   (setting claims) smaller+higher, subject props larger; at most ONE `xl` per frame.
5. **Readability proof** — for the canonical two-pole+relator scene, `composeFrame`
   must emit a machine-checkable layout certificate
   `{polesSeparate: true, relatorAnchored: true, allInSafeArea: true}` — part of
   `visualCompiled`, verifiable without rendering.
