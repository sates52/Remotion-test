## 2. Design — Strategy → requirement → Contract Evidence → Firewall

### 2.1 Single-writer rule

The **planner is the only writer of `_visualStrategy`** (decided once, on the final assembled scene, after contract repair and the staging lock). The firewall **never reads `_visualStrategy`** — it reads `visualContract.visualEvidence.representation`, i.e. contract evidence, and judges the real scene against it. Metadata mutation cannot move a verdict (tested).

### 2.2 Record schema (additive `_visualStrategy`, following `_authorship`/`_semanticAdapter`)

```jsonc
"_visualStrategy": {
  "strategy": "RELATION_LOCK",            // from PHASE B decideStrategy (unchanged)
  "risks": ["RELATION"],                  // unchanged
  "capabilityConfidence": null,           // unchanged
  "semanticSignature": { ... },           // unchanged (PHASE E consumes)
  "levers": ["lookAt:partner|motif", ...],// unchanged (declaration, not evidence)
  "requirement": { "kind": "relation", "parties": ["manager","employee"],
                   "shots": ["twoShot","split","overShoulder"], "lookAt": "partner" },
  "evidence": { ... },                    // unchanged (PHASE B)
  "provenance": { "decidedAt": "plan", "capabilityMap": "data/visual-capability.json" },
  "note": "declarative metadata — the record of a decision, never a trusted flag; ..."
}
```

### 2.3 Requirement mapping (renderer-verified lever names)

Renderer facts: `props[].arc ∈ {none,grow,shrink,rise,fall,closein,tilt,break}` (`src/engines/antidote/schema.ts:386`), text style `"strike"` (`schema.ts:422`), shots/expressions/emotions/lookAt as in PHASE B.

| Strategy | `requirement` | Firewall binds to (real scene fields) |
|---|---|---|
| `DIRECT_SCENE` | `null` | no evidence key, no new checks (books unchanged) |
| `CONTRAST_ABSENCE` | `{kind:"absence", textStyles:["strike"], propArcs:["shrink","closein"]}` | ≥1 named lever present: some `texts[].style === "strike"` OR some `props[].arc ∈ propArcs` |
| `ABSTRACT_CONCRETE` | `{kind:"concrete", shots:["illustration","diorama","insert"], diagramAllowed:true}` | `scene.shot ∈ shots` OR `scene.diagram` truthy |
| `EXPLICIT_STATE` | `{kind:"state", expressions:[…], emotions:[…]}` (from the strategy's evidence) | ≥1 character whose `expression ∈ expressions` OR `emotion ∈ emotions` |
| `RELATION_LOCK` | `{kind:"relation", parties:[subject,object], shots:["twoShot","split","overShoulder"], lookAt:"partner"}` | ≥2 characters AND `scene.shot ∈ shots` AND both parties map to on-screen `identity`/`role` AND ≥1 character has `lookAt === "partner"` (lookAtFor already binds it at plan time, :732-736) |
| `SAFE_REPRESENTATION` | `{kind:"fallback", lever:"shot:diorama", confidence:0.938}` | `scene.shot === lever.shot` — the measured-safe declaration becomes a checkable scene fact |
| `UNRESOLVED` | `null` + `reasons` recorded in the strategy record | **no enforcement in C** (report-only: counted in the plan summary); hard-gating stays with D (open question a) |

### 2.4 Enforcement semantics (`validateScene`)

New block after the existing evidence checks (:186-198), reading **only** `contract.visualEvidence.representation`:

- absent → no check (pre-C books and `DIRECT_SCENE` unaffected — backward compatible);
- present but malformed → `STRATEGY_EVIDENCE_MALFORMED` (hard);
- present and unsatisfied by the scene → `STRATEGY_REQUIREMENT_UNMET` (hard), message names scene id, requirement kind, and the exact unmet binding.

The firewall gains **no** reference to `_visualStrategy` anywhere; `grep`-able, plus the negative test in §4.

### 2.5 Why the requirement is copied by inject-provenance (not created by the planner)

P1.1 rule (:979-983 comment): an absent contract must fail the firewall, not become a fake PASS — so the planner never fabricates `visualContract`. The planner writes the requirement into `visualEvidence.representation` **only when the scene already carries a contract** (authored-brief books, :983); for generic books, `inject-provenance.js` — which already creates `visualEvidence` for every scene and already runs with `--force` in the standard flow before the firewall (§1.2) — copies `scene._visualStrategy.requirement` into `visualContract.visualEvidence.representation`. Merge semantics: **additive key only**; `subjects`/`relations`/`states`/`characterIntent` are never touched.

### 2.6 Semantic-preservation guarantees

C performs exactly two writes per scene: the new `_visualStrategy` key, and the additive `visualEvidence.representation` key (when a contract exists). Authored `action`, `subject`, `relation`, `state`, `world`, `metaphor` are untouched; `sanitizeAction` call sites (:767/:838) untouched (D); `decideStrategy` stays pure (zero-mutation test exists since PHASE B).
