## 5. Ordering fix (operator D review, post-5c7dc3d)

The operator found a sequencing bug in the first D commit: `resolveStrategy` ran AFTER the staging lock, so the lock sealed the authored-external action (`push`) while the scene shipped the repaired one (`point`) — two truths, and `gate-authorship --restore` would have resurrected the schema-external action straight into a D4 hard failure.

**Fixed ordering (now the contract, source-guarded):**

```text
applyContractRepair → decideStrategy → resolveStrategy (repairs) → record → STAGING LOCK
```

- the lock seals the REPAIRED action — `gate-authorship --restore` restores the enum-valid repaired value and can never resurrect the authored-external original (the authored original lives in the art file + the resolution record's from→to);
- the record's `semanticSignature` is refreshed over the repaired final scene — the record describes what ships, so PHASE E will never read the recorded repair as a post-plan mutation (the resolution documents the authored→final delta);
- the plan summary counts `repaired` scenes separately (a repaired scene is NOT unresolved — its repairs superseded the enum-caused UNRESOLVED record and the firewall passes it).

Regression tests added (test-action-lifecycle.js, 35→44): lock.action === repaired value; drift detection + `--restore` writes back the repaired action (can never flip to the authored-external one); source-ordering guard (`decideStrategy → resolveStrategy → lock` enforced by index comparison); signature-refresh guard. Full suite 250 green. After-smoke re-run: identical numbers (the WWL smoke book is heuristic and carries no enum-invalid actions — the fix is proven by the ordering tests, not by a count change).
